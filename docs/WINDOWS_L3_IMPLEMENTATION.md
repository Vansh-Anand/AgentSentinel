# Windows L3 execution and ETW observation

The faculty launcher enables `AGENTSENTINEL_WINDOWS_JOB_REQUIRED=1`. After L2 authorization and a durable decision record, each permitted lab action runs in a fresh trusted Python worker. The server configures a Windows Job Object, verifies the worker is assigned, then sends the action over a bounded stdin packet. A failed setup never releases the action.

The Job Object sets a 384 MiB process memory limit, one active process, and kill-on-close. The supervisor enforces a 10-second action timeout and terminates the job on timeout or cancellation. The worker reconstructs the server-owned `LabPolicy`, verifies its hash, and runs only the five declared application tools. Model credentials are excluded from its environment. L2 still owns file and tool permissions; the Job Object is a resource and lifetime control, not a filesystem or network sandbox.

The signed L3 action receipt contains `job_assigned`, `action_released`, completion state, worker PID, applied limits, duration, termination reason, application effects, and ETW status. A forbidden `.env` action is denied before any worker starts in a direct-request run. The Results screen shows these fields. The Layer Trace replays persisted Job creation, limit setup, worker assignment, action release, ETW status, and worker completion events from the backend. Document-injection runs still read the edited README as an explicit setup action.

ETW process observation uses the Windows `Microsoft-Windows-Kernel-Process` provider's process keyword (`0x10`) through `logman`, then converts the bounded trace with `tracerpt`. A correlated partial result requires a provider-matched **process start event (ID 1)** for the worker PID, its UTC `CreateTime` inside the worker launch window, and an explicit zero lost-event count. Process stop events (ID 2) are supporting lifecycle observations; unrelated same-PID events are ignored. The trace receipt reports scanned and matching events, whether process start was observed, and event loss. An absent or unparseable loss summary is **unknown**, never zero. This is limited to process lifecycle events. It does not establish full file/network effects or prevent an operation. The direct unelevated collector records `ETW_ADMIN_PERMISSION_REQUIRED` and `coverage=NONE` on this host.

For a live ETW website demo, run `./scripts/start_etw_demo.ps1 -ApiPort 8010 -UiPort 5180 -EtwPort 8011` and accept the Windows elevation prompt for the **broker only**. Open `http://127.0.0.1:5180/lab`. The API and UI stay unelevated. The broker binds to `127.0.0.1`, requires a random per-demo token stored under ignored `.data/faculty-demo` with a restricted file ACL, accepts only start/stop/shutdown of a fixed process provider, limits simultaneous sessions, returns only bounded PID-correlated lifecycle metadata, and deletes raw traces after each action. The token is excluded from the action worker's environment. `./scripts/stop_faculty_demo.ps1` stops the API, UI, and broker. The ordinary `start_faculty_demo.ps1` still works without ETW rights and reports coverage honestly.

The standalone `python scripts/verify_windows_etw.py` remains available for a focused elevated collector test. Its actual Windows trace exposed a `tracerpt` local `TimeCreated` offset of `+05:29` on this `+05:30` host; correlation now uses the provider's UTC `CreateTime` field. The elevated test observed the spawned process's start and stop event with zero reported loss. In the browser, a fixture calculation and a custom Ollama calculation both showed `CORRELATED_PARTIAL`; a forbidden `.env` read stopped at L2 without a worker. An elevated session alone is not proof of correlation: inspect the worker PID, process-start event, and loss field in each receipt.

Run `python -m unittest tests.runtime.test_windows_l3 -v` for real Job Object assignment, allowed execution, pre-dispatch denial, child-process limit, memory-limit failure, timeout termination, setup-failure refusal, signed-receipt tamper detection and ETW event-correlation parsing. Run `python -m pip install -r requirements-test.txt` to install the Windows-only `pywin32` dependency. The Windows CI job repeats these tests. Unit parser fixtures prove the correlation rules, not that this host collected ETW events.

The prior Linux eBPF and TPM modules are separate opt-in paths and are disabled by the Windows launcher. The Windows release claims Job Object containment and application effects only when the per-run receipt verifies them. It does not claim native eBPF or TPM proof.

The 50-case fixture evaluation exercises bounded capability contracts, not arbitrary semantic attack detection. Any source change invalidates its manifest binding until the baseline is reapproved and the evaluation rerun. ETW correlation is observable only in runs that actually use the elevated broker or another trace-controller context.
